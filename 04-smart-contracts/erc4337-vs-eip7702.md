# ERC-4337 vs EIP-7702：兩種「智能帳戶」對 CEX 充提嘅分別

> 銜接：09 月講過 [ERC-4337](./erc4337-account-abstraction.md)，10-05 講過 [EIP-7702](./eip7702-eoa-delegation.md)。今日唔再逐個講，而係**擺埋一齊比**，同埋講 CEX 後端要點改。

## 人話

- **4337**＝用戶**開一個新嘅合約帳戶**（新地址）。佢唔直接發 tx，而係交 UserOperation 畀 Bundler，Bundler 發一筆普通 tx 去 `EntryPoint`，EntryPoint 再 call 用戶個合約帳戶。協議完全冇改。
- **7702**（Pectra 升級引入，type `0x04` tx）＝**舊 EOA 地址唔變**，簽一個 authorization，令呢個 EOA「掛上」一份合約代碼（`getCode` 會見到 `0xef0100` + 20 bytes 委託地址）。私鑰仍然全權話事。
- 兩者可以疊埋用：EOA 經 7702 委託去一個兼容 4337 嘅帳戶實現，之後就可以走 EntryPoint／Paymaster。

用 CEX 嘅講法：4337 似「幫客開一個新子帳戶，由代辦（Bundler）幫佢落單」；7702 似「原有帳戶號碼唔變，但裝咗一套自動化規則」。

## 面試短答（對比表）

| | ERC-4337 | EIP-7702 |
|---|---|---|
| 協議改動 | 冇，靠 EntryPoint 合約 | 有，新 tx type 0x04 |
| 地址 | 新合約地址（多數 CREATE2 預先算出） | 沿用原 EOA 地址 |
| `getCode` | 完整 bytecode／proxy；未部署前係空 | 23 bytes：`0xef0100` + delegate |
| 私鑰 | 帳戶規則話事，可以冇單一私鑰 | EOA 私鑰仍可做任何嘢、可改／撤委託 |
| nonce | EntryPoint 入面嘅 2D nonce（key + seq） | 協議 nonce；authorization 都會推進 nonce |
| 鏈上 `tx.from` | Bundler 地址，唔係用戶 | 用戶 EOA（或者幫佢代發嘅 relayer） |
| 驗簽 | EIP-1271（未部署可能要 ERC-6492） | ecrecover 仍有效；帳戶亦可另外實現 1271 |

**CEX 一句總結：** 兩者都令「收幣嘅地址」可能有代碼、「錢可能喺 internal call 入面郁」，所以充值唔可以靠 `tx.to`、出金唔可以寫死 21000 gas、綁定驗簽唔可以只用 ecrecover。

## 常見追問（連答案）

**Q1：用戶由 4337 帳戶提 ETH 去你 CEX 充值地址，點解你個掃描器可能漏單？**  
A：條鏈上 tx 係 `Bundler → EntryPoint.handleOps`，ETH 係喺 internal call（EntryPoint → 帳戶 `execute` → 你地址）先轉過嚟。只睇 `tx.to == 充值地址` 就會漏。Native ETH 要用 trace（`debug_traceBlock`／callTracer）或者每塊對充值地址做 balance diff 兜底；ERC-20 冇呢個問題，因為睇 `Transfer` log，同 tx 係邊個發無關。7702 帳戶 batch 轉賬一樣會出現 internal call，所以兩者處理方法一樣。

**Q2：用戶畀一個 4337 地址叫你出金，地址 `getCode` 係空，出唔出？**  
A：可以出。4337 帳戶地址係 counterfactual（未部署已經可以收錢），首次 UserOp 帶 `initCode` 先部署。但要提醒兩點：(1) **唔好假設同一地址喺其他鏈都屬於佢**：合約帳戶地址取決於 factory 同初始化參數，另一條鏈未必部署到同一地址，揀錯鏈出金可能永久鎖死，前端要強調「只限呢條鏈」；(2) 已部署嘅合約收 ETH 會跑 `receive`，gas 要 `estimateGas`，唔好寫死 21000，失敗要入「可重試／人工」狀態。

**Q3：Smart account 用戶綁定提現地址或者登入簽名，後端點驗？**  
A：先 `getCode`：
- 冇 code 嘅 EOA 就用 ecrecover；
- 有 code（4337 帳戶或 7702 委託）就 call `isValidSignature`（EIP-1271），回 `0x1626ba7e` 先算過；
- 未部署嘅 4337 帳戶，簽名可能用 ERC-6492 包住（入面帶 factory 資料），要用支援 6492 嘅 verifier。
7702 EOA 用 ecrecover 仍然驗得到，因為私鑰冇變；但如果產品規則係「以合約規則為準」，就應該走 1271。

**Q4：7702 對 CEX 有咩新安全風險？**  
A：
- **騙簽 authorization**：簽一個委託去惡意合約，等於將成個帳戶交出去。`chainId = 0` 嘅 authorization 喺所有鏈都有效，殺傷力更大。
- **`tx.origin == msg.sender` 唔再代表「呢個係冇代碼嘅 EOA」**：靠呢招防合約調用嘅邏輯會失效。
- **自家熱錢包／充值地址突然出現 delegation designator**，即係私鑰可能已經洩漏，要當 P0 安全事件處理（10-05 講過）。

**Q5：4337 嘅 nonce 同你出金 nonce 管理有咩關係？**  
A：冇直接關係。4337 nonce 存喺 EntryPoint，按 `(sender, key)` 分開排序，可以並行；Bundler 自己 EOA 嘅協議 nonce 係另一套。如果 CEX 自己用 4337 出金，就要分開追蹤兩套 nonce：UserOp nonce 管業務冪等，Bundler nonce 管上鏈卡單／RBF。同 10-07 Safe 嗰課一樣，業務 nonce ≠ executor nonce。

## 小練習（題目後即附參考答案）

**題：** 審計發現：上個月有 3 筆用戶話「已經充咗 ETH」嘅單冇入帳。鏈上睇到三筆 tx 都係打去 `0x5FF1…`（EntryPoint），`status = 1`。你點排查同修？

**參考答案：**
1. 用 `debug_traceTransaction`（callTracer）睇 internal calls，確認有冇 `value > 0` 嘅 call 打去我哋充值地址，同埋嗰層 call 有冇 revert（外層 status=1 唔代表每層 internal call 都成功）。
2. 確認後經人工補單，必須行同一套冪等 key（例如 chain + txHash + traceAddress），防止之後重掃再入一次。
3. 根治：native 充值偵測加 trace 掃描，或者對充值地址每塊做 balance diff 兜底；同時用 Q1 嘅方法比對「掃描入帳」同「鏈上餘額變化」，對帳有差異就報警。
4. 回顧影響範圍：其他走 internal call 嘅來源（7702 batch、Safe、DEX router）一齊覆蓋。
