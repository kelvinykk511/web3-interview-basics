# 代幣合約遷移／換幣（例如 MATIC → POL）：交易所後端要做咩

## 人話
項目方有時會「換一隻新合約」：改名（MATIC→POL）、改 decimals／總量（redenomination，例如 1 舊 = 100 新）、或者舊合約有漏洞要遷移。鏈上其實係**兩隻完全唔同嘅代幣**（唔同合約地址），只係項目方話佢哋「等價」。交易所要負責幫用戶換，而且舊合約嘅充值仲會繼續有人打入嚟。

## 面試短答
代幣遷移喺鏈上係新舊兩個獨立合約，交易所要當成一次有計劃嘅資產遷移：先停舊幣充提和交易（或保留交易一段時間），喺快照時間點按換算比例把用戶舊幣餘額轉成新幣（帳本內部記一筆 conversion 流水），同時用熱/冷錢包裏面嘅舊幣經項目方 migration 合約換成新幣，再對帳確保「用戶新幣負債 ≤ 鏈上新幣資產」。之後新合約開充提；舊合約充值唔好直接消失，要麼按比例自動換，要麼走人工找回。

## 常見追問（連答案）
**Q1：帳本點樣記先唔會出錯？**
A：唔好直接改幣種名或者 update 餘額。舊幣同新幣係兩個 asset_id，換幣用一張 conversion 單：扣舊幣、加新幣，兩邊流水用同一個 conversion_id，冪等可重跑；比例用整數最小單位計，舊新 decimals 唔同時要明確換算，捨入餘數（dust）記入一個專門帳戶，唔好默默食咗或者多畀。

**Q2：凍結中途仲有人充舊幣、有掛單點算？**
A：快照前先撤銷舊幣交易對所有掛單、停提現；充值掃描繼續跑，快照後入帳嘅舊幣充值標記為「遷移後到帳」，用同一套 conversion 規則補換（或者入人工找回隊列）。理財／槓桿／借貸倉位要單獨處理，例如先平倉或按比例轉換抵押品。

**Q3：鏈上舊幣點樣換？風險喺邊？**
A：一般 approve 項目方嘅 migration 合約再 call `migrate()`，或者項目方直接 airdrop 新幣畀交易所地址。風險：approve 錯合約（釣魚假 migration 合約）、無限授權、分多個錢包/冷錢包要逐個簽。做法：合約地址要從項目方官方公告 + 鏈上驗證核對，授權精確金額，先小額試換，冷錢包按 safe 多簽流程批。

**Q4：點樣知道換齊咗？**
A：換之前：sum(用戶舊幣) vs 鏈上舊幣總持倉；換之後：sum(用戶新幣) 應該等於鏈上新幣持倉 −/+ 已知差額（未換完嘅舊幣、dust 帳戶、手續費）。缺口要能逐筆解釋，否則唔開提現。

**Q5：ticker 冇改但合約改咗（例如 USDT 某鏈換合約）有咩坑？**
A：掃描器仍然用舊合約地址白名單，新合約充值會「冇到帳」；或者兩隻都監聽導致新舊混記。所以代幣配置以 (chain, contract) 為主鍵，唔係 symbol；切換要有生效時間點，前端充值頁同步更新合約地址提示。

## 小練習（題目 + 參考答案）
**題目：** 舊幣 decimals=18，新幣 decimals=18，比例 1 舊 : 1000 新（redenomination）。用戶有 0.0000000000000012345 舊幣（最小單位 1234500... 你自己設計）。另外換完後交易所鏈上發覺新幣比用戶總負債少咗 0.3%。你點處理？

**參考答案：**
1. 全程用最小單位整數：新幣數量 = 舊幣最小單位 × 1000（decimals 一樣就直接乘），乘法唔會產生捨入；如果係除法比例（例如 1000 舊 : 1 新）就 floor 落去，餘數入 dust 帳戶並記錄。
2. 0.3% 缺口唔好當作誤差：逐項排查——有冇冷錢包未換、migration 合約有冇收手續費、快照後補換嘅舊幣算未、有冇 fee-on-transfer 行為、項目方 airdrop 有冇少發。
3. 解釋唔到之前：限制新幣提現額度或暫停提現，同項目方對數；最終缺口由交易所補足（資產 ≥ 負債係底線），唔可以向用戶按比例扣減。
