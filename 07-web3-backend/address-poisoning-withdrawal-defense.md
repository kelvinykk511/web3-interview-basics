# 地址投毒（Address Poisoning）同出金防護

> 銜接：[地址投毒／零額 Transfer（CEX 充值掃描）](../06-security/address-poisoning-deposit-scan.md) 講掃鏈側；呢篇講出金／地址簿防護。

## 人話
騙徒整一個頭尾幾個字同你常用地址一樣嘅地址（例如 0x1234…abcd），再向你打 0 金額或者假幣轉帳，令佢出現喺你嘅交易記錄。下次你喺記錄度「複製上次地址」，就複製咗騙徒嗰個。

## 點做到
- **0 金額 transferFrom**：標準 ERC-20 檢查 allowance >= amount，0 >= 0 成立，所以任何人都可以 transferFrom(你, 騙徒, 0)，鏈上出現 from＝你嘅 Transfer 記錄，好似你自己打過俾佢。
- **假 token 合約**：自己 emit 任意 from/to 嘅 Transfer event。
- **小額 dust**：真錢但好少，令記錄更似真。
- **Vanity 地址**：頭 4 + 尾 4 個 hex 約 16^8 ≈ 43 億次嘗試，GPU 好快就搵到。
- 案例：2024 年 5 月有人因此打錯約 1,155 WBTC（約 6,800 萬美元），後來大部分被歸還。

## 面試短答（30 秒）
地址投毒係利用人只睇頭尾：騙徒生成頭尾相同嘅 vanity 地址，用 0 金額 transferFrom 或假 token 污染交易記錄，等人複製錯地址。EIP-55 checksum 防唔到，因為呢個係合法地址。交易所要兩邊防：對用戶，出金地址簿／白名單 + 冷靜期、新地址同歷史地址做頭尾相似度偵測、UI 顯示完整地址、記錄唔顯示 0 金額或未上架 token；對自己，充值掃描忽略 0 金額同非白名單合約，內部資金調撥（熱轉冷、做市商）只准由系統地址簿揀，唔准由 explorer 手動複製。

## 常見追問（連答案）
1. **點解 0 金額 transferFrom 唔使 allowance？** allowance 檢查係 >= amount，0 永遠過，而且實現照 emit Transfer，所以 from 可以係任何人。
2. **用戶睇頭尾 4 位夠唔夠？** 唔夠，騙徒就係針對頭尾；系統要全地址比對，並偵測「頭尾一樣但唔相等」。
3. **EIP-55 checksum 幫唔幫到？** 唔幫，checksum 只防打錯字，投毒地址本身合法、checksum 正確。
4. **用戶已經打咗出去點算？** 鏈上不可逆；可以聯絡 USDT/USDC 發行方凍結、通報、KYT 標記騙徒地址。重點喺事前攔截。
5. **對交易所充值掃描有咩影響？** 假 Transfer／0 金額記錄唔可以入帳或者推通知，只認白名單合約同正金額，入帳以自己掃描同 receipt 為準。

## 小練習
**題**：產品要做「出金地址相似度告警」，你點設計？寫出比對對象、規則、處理動作。

**參考答案**：
- **比對對象**：用戶地址簿、過去 N 日成功出金地址、用戶充值來源地址、平台已知地址。
- **規則**：同一條鏈；新地址唔等於任何已知地址，但同某已知地址頭 4+ 同尾 4+ 個字符一樣 → 高風險；如果新地址曾經向該用戶相關地址打過 0 金額或垃圾 token → 更高風險。
- **動作**：唔俾直接提交；並排顯示兩個完整地址並高亮差異；要求重新輸入或延遲（例如 24 小時）／客服複核；記錄事件並將地址加入風險庫（KYT）。
- **實作**：預先建索引 key＝chain + 頭 8 hex + 尾 8 hex，方便快速查相似地址。
