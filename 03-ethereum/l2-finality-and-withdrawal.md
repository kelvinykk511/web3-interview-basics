# L2 最終性與提款延遲（CEX 視角 · 輕刷）

## 人話（從你熟的 CEX）

L1 你習慣「等 N 個 confirmation 就當最終」。L2 多一層：

- **Soft finality**：sequencer／L2 節點話「已打包」——UX 幾秒，但仲可重組、審查、或（optimistic）被挑戰影響
- **Hard finality**：狀態已喺 L1 落地到足夠安全（output／state root 最終、或 ZK proof 已驗證）——逆轉成本極高

入金（用戶 → CEX 喺 L2）同出金（用戶要「提到 L1」）**唔好共用同一個 confirmation 常數**。產品顯示「Arbitrum 到帳」可以好快；官方橋 L2→L1 往往有 **challenge window（樂觀卷軸常見約 7 日量級）** 或 **ZK 證明／打包延遲**。CEX 多數用自有多鏈熱錢包＋內部 ledger 對沖，對外 SLA 同背後橋路徑要分開講。

類比：銀證轉帳「銀行已受理」≠「證券戶可賣」；soft confirm 似受理，hard／橋完成似真正可動用。

## 面試短答

- Rollup：執行在 L2，資料／證明提交 L1。**Optimistic**：先假設正確 + 挑戰期 → L2→L1 提款要等窗結束。**ZK**：有效性證明後 L1 釋放通常快過樂觀，但仍受 prove／L1 擁塞影響。
- CEX **入金政策**：小額可偏 soft＋深度；大額傾向等更硬最終性（L1 post／多確認／風控額度分檔）。
- CEX **用戶提幣 SLA**：目標鏈若係 L2，多數係 L2 熱錢包直出；若用戶要 L1，可能官方橋（長）、流動性橋／第三方 fast withdraw（快但有橋對手／合約風險）、或內部 L1 庫存墊付。
- **產品鏈 ≠ 內部調撥**：用戶選「ETH-Arbitrum」只决定簽名／RPC／確認規則；資金從邊個熱錢包出、要唔要跨層，係 treasury 路徑。
- 同 sequencer 風險正交：soft confirm 快唔代表審查／宕機下你仍能出金（見 sequencer 筆記）。

## 常見追問（連答案）

**Q：Soft vs hard finality，CEX 點用？**  
A：Soft 服務體驗同細額入帳；hard（或「已安全 post 到 L1」）服務大額入帳、內部劃轉完成、對帳結算。面試講清風險權衡，唔好背「一律 12 確認」。

**Q：Optimistic 挑戰窗 vs ZK prove 延遲，對提款 SLA 有咩差別？**  
A：樂觀官方橋：挑戰期係協議安全下限，短唔到「幾分鐘」。ZK：瓶頸多在證明產生同 L1 驗證／排隊，通常短過 7 日但唔係即時。對外文案要分開「L2 內轉」同「跨回 L1」。

**Q：入金確認政策 vs 用戶見到嘅「提幣到 L1」SLA，點解要兩套？**  
A：入金係 CEX 承擔 reorg／欺詐／sequencer 風險換速度；提幣到 L1 往往受橋協議或流動性路徑約束。混成同一常數會要麼入帳過慢、要麼承諾做唔到嘅即時 L1 到帳。

**Q：流動性橋／fast withdraw 同官方橋差在邊？**  
A：官方橋：信任最小化、延遲長。流動性橋：LP／協議先喺目標鏈墊資，用戶快到，換來智能合約、LP 償付、费率、同可能嘅審查／暫停風險。CEX 若用嚟滿足「快提 L1」，要當 **對手方＋合約風險** 入風控，唔好當「免費縮短挑戰期」。

**Q：大額 L2 入金，等 soft 就入帳有咩問題？**  
A：短窗 reorg、sequencer 異常、或（極端）錯誤狀態被挑戰前你已兌出法幣／提到其他鏈 → 虧損。實務：額度分檔、延遲入帳、或等 L1 批次／output 公佈再放行大額。

## 小練習

**題：** 大戶要求「L2 上的 ETH 快提到 Ethereum L1」，客服承諾 10 分鐘到帳。Ops 提議走流動性橋（fast path），唔走官方橋。風控叫你評估：對用戶 SLA、對 CEX 庫存／風險、同狀態機要多啲咩欄位？什麼情況你會拒絕 fast path、改為官方橋或內部 L1 熱錢包墊付？

**參考答案：**  
- **SLA**：流動性橋可滿足「約 10 分鐘」體驗；官方橋做唔到（挑戰窗）。若承諾已出口，要嘛 fast path、要嘛 CEX 用 **L1 自有庫存墊付**（內部 treasury rebalance 稍後再用官方橋／批量搬磚補回）——後者風險在自己手上，唔經過第三方橋。  
- **風險**：流動性橋 = 合約漏洞、LP 暫停、錯誤鏈／錯誤資產、橋费率滑點；大額要有白名單橋、額度上限、超額改墊付或拒絕即時。  
- **狀態機**：`created → bridging_fast (bridgeTx) → l1_seen → confirmed`，失敗要有 `bridge_failed`／人工；同官方橋路徑 `l2_initiated → … → challenge_elapsed → l1_claimable` 分開，唔好共用一個 `confirmations=N`。  
- **拒絕 fast path**：橋唔喺白名單、額度超限、橋健康檢查失敗、或合規要求最小化信任——改 L1 熱錢包直出（有庫存）或告知官方橋長延遲並改 SLA。核心：產品「到 L1」可以由 **內部庫存** 滿足，唔等於用戶款必須同一筆官方橋 tx。
