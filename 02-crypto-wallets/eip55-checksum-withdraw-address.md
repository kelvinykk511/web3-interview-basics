# EIP-55 Checksum／提現地址校驗（CEX）

## 人話（從你熟的 CEX）

用戶填提現地址：一串 0x + 40 個 hex。Ethereum 地址本身**唔區分大小寫**（底層係 20 bytes），但人眼／客服複製好易錯一位。EIP-55 用地址嘅 hash 決定邊啲字母大寫，做成一種**內建校驗和**——寫錯一位，checksum 多數會對唔上，後端可以拒絕。

類比：銀行帳號最後一位 check digit，或者信用卡 Luhn——唔係加密，只係防手殘／傳輸破壞。CEX 提現表單同出金簽名前，都應該過呢關（外加 chain／合約／memo 規則）。

## 面試短答

- **底層地址**：20-byte；展示成 `0x` + 40 hex。全小寫／全大寫都「合法」，但**無 checksum 保護**。
- **EIP-55**：對「去掉 0x 嘅小寫 hex」做 `keccak256`，按 hash 對應 nibble 決定該位字母是否大寫。驗證：重新計算預期大小寫，必須完全一致。
- **CEX 提現校驗流水線（常見）**：格式（0x + 40 hex）→ EIP-55（若用戶帶混合大小寫）→ 禁止合約地址出金（可選 `eth_getCode`）→ 黑名單／制裁名單 → 幣種規則（memo／tag、最小額）→ 再進簽名出金。
- **全小寫輸入**：嚴格 EIP-55 會「永遠通過格式但無錯誤檢測」。產品策略常見：(a) 接受全小寫但強制回顯成 checksum 地址請用戶二次確認；(b) 或要求必須帶正確 checksum。面試講清楚 trade-off：可用性 vs 防錯。
- **同其他鏈**：BTC 有 Bech32／Base58Check；Tron Base58Check；唔好用同一套「只數長度」跨鏈。多鏈路由要按 `chainId`／網絡選校驗器。

## 常見追問（連答案）

**Q：EIP-55 能唔能當簽名／證明「用戶擁有呢個地址」？**  
A：唔能。Checksum 只證明字串冇抄錯；擁有權要簽名挑戰（personal_sign／EIP-712）或看鏈上控制。綁定提現地址 ≠ 證明私鑰在你手。

**Q：用戶貼全小寫地址，你哋系統應該 reject 定 accept？**  
A：兩派都常見。Accept：相容錢包／瀏覽器複製習慣，但要 UI 回顯 checksum 並二次確認，後端存 canonical checksum 形式。Reject：減少靜默錯字，但客訴會多。重點係**唔可以**「全小寫直接當已校驗正確」。

**Q：點解仲要 `eth_getCode(address)==0x`？**  
A：Checksum 過唔代表係 EOA。轉去合約可能卡住資金（合約無 withdraw）或觸發奇怪 `receive`／`fallback`。不少 CEX 對「普通幣提現」禁合約地址，或只允許白名單（例如已知 bridge）。合約錢包／Smart account 要產品明確支持。

**Q：地址投毒（相似地址）同 EIP-55 關係？**  
A：Checksum 主要防**隨機錯位**，防唔到攻擊者刻意構造視覺相似地址（前綴後綴相同）。仍要完整顯示、白名單、小額試提、禁止「從最近 from 一鍵填」。同 09-25 投毒筆記互補。

## 小練習

**題：** 提現 API 收到 `to=0xabCDef...`（混合大小寫但你重算 EIP-55 對唔上）、另一請求 `to=0xabcdef...`（全小寫、對應真實用戶錢包）、第三個 `to` checksum 正確但 `eth_getCode` 非空。三單應點處理？庫內地址點存？

**參考答案：**  
1. 混合大小寫但 checksum 錯 → **直接拒絕**，錯誤碼明確「地址校驗失敗／請檢查大小寫」，唔好「自動改寫」後靜默出金。  
2. 全小寫 → 按產品策略：若允許，正規化成 EIP-55 回顯給用戶確認（或確認頁強制展示 checksum）；庫內存 checksum 或一律小寫 bytes＋展示層 checksum，但簽名前用嘅 `to` 必須係用戶確認過嗰個 20-byte。  
3. checksum 對但係合約 → 拒絕或走「合約地址提現」專用審批／白名單；普通 ERC-20／ETH 提現預設拒。  
冪等同風控鍵用 `chainId + to_bytes + userId`，唔好用「展示字串大小寫」當唯一鍵。
